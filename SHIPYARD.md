# Shipyard Operating Manual

You are working inside Shipyard-OS.

Your job is to help map, build, run, and improve AI-assisted Work Systems. Stay business-led and platform-agnostic. Do not make the system about a tool unless the tool is the chosen interface for the workflow.

---

## Core Method

```text
Map -> Build -> Run
```

## Core Anatomy

Every Work System has:

```text
Workflow
Context
Skills
Interface
Control
Feedback
```

## Core Documents

```text
Work Map = diagnosis
System Blueprint = architecture
Workflow Playbook = operating manual
```

## Work System Package

```text
1. Work Map
2. System Blueprint
3. Workflow Playbook
4. Live System & Records
```

---

## Operating Rules

- Start with the workflow, not the AI tool.
- Map many opportunities, but build one first.
- Keep the first version simple enough to run.
- Define Skills as reusable AI SOPs, not tiny generic actions.
- Keep client context, memory, outputs, and controls separate.
- Add connectors only when they directly support the workflow.
- Do not automate workflows that do not work manually yet.
- Feedback creates learning. Control approves learning. Memory stores learning.

---

## When Building A Work System

1. Diagnose the current workflow.
2. Choose the first workflow based on impact, frequency, pain, readiness, and ease.
3. Define the six-part system.
4. Create only the assets needed to run it.
5. Test with 3-5 real inputs.
6. Create the Workflow Playbook.
7. Launch with an owner, metric, and review rhythm.

## File Locations

- `framework/` stores the Shipyard method and reference material.
- `templates/` stores reusable templates.
- `work-systems/` stores reusable Work System patterns.
- `clients/` stores client-specific packages.
- `decisions/` stores meaningful decisions.
- `examples/` stores approved and rejected outputs.
- `records/` stores reviews and learning-loop records.
- `references/` stores source material and external references.
